# 开发文档：构建编程智能体（Coding Agent）— 草稿

> 依据《软件工程专业推免项目：构建编程智能体》题目制定。本文档随 grill-me 审议迭代，最终定稿后作为开发路线图。

## 0. 题目约束（不可违反的硬性红线）

- 独立设计并实现一个 **coding agent**：与大模型交互、自主读写文件、执行命令、完成交给它的编程任务。
- **禁止**：对现成 agent 产品封装界面；使用任何 agent 框架/SDK（LangChain、LlamaIndex、OpenAI Agents SDK、Claude Agent SDK、AutoGen、CrewAI 等）。
- **允许**：模型厂商 API 客户端库、OpenAI 兼容网关、模型原生 tool calling 接口；模型、语言不限。
- **必须自研**：对话历史与上下文管理、工具定义与本地执行、模型输出解析、循环终止条件、错误处理。
- **禁止**：依赖 API 服务端托管的代码执行/文件工具（Code Interpreter、Files API）。
- API key 一律通过环境变量或未入库配置文件，不得进仓库/README/视频。
- 截止：**2026-09-02 24:00（北京时间）**。三份提交物：公开 Git 仓库、README.txt（≤1000 汉字）、≤2 分钟 mp4 视频（≤200MB）。面试会追问"为什么这样运转、能否为设计决策辩护"。

## 1. 总体设计目标

做"一个能自己看仓库、改代码、跑测试、反复试错直到完成任务"的 CLI agent，并且**能用一套自动评测系统客观衡量它到底行不行**。评测不是附属品，而是本项目评分/自辩的核心证据。

## 2. 可参照的开源项目（调研结果）

### 2.1 编码智能体（重点看其"工程结构"而不是代码）
| 项目 | 仓库 | 亮点（我们可借鉴的） |
|---|---|---|
| SWE-agent（Princeton） | https://github.com/SWE-agent/SWE-agent | 把 agent 与 CLI 交互抽象成"Agent-Computer Interface"（ACI），设计了专门的命令封装层；这是解决"模型不熟 shell"的关键思想 |
| OpenCode（sst） | https://github.com/sst/opencode | 终端 TUI 化编码 agent；工具（tool）注册 + 本地执行 + 会话管理的简洁实现，TS 栈 |
| Aider | https://github.com/Aider-AI/aider | 纯命令行、无需感知上下文的 repo 编辑；git 集成 & 自动 commit，上下文裁剪策略成熟 |
| OpenHands（前 OpenDevin） | https://github.com/All-Hands-AI/OpenHands | 完整 agent 运行时 + 事件流 + 沙箱执行（docker）；工具层与安全隔离设计 |
| Anthropic Claude Code | （闭源，作目标参照） | 交互式会话、权限确认、工具调用循环的产品形态参考 |

### 2.2 自动评测系统（"AI 可驱动评测"）
| 项目 | 仓库 | 借鉴点 |
|---|---|---|
| SWE-bench | https://github.com/SWE-bench/SWE-bench | 标准软件工程 agent 评测：任务=真实 GitHub issue，解=针对 repo 生成的 diff/patch，判定=在隔离环境跑测试，PASS/FAIL |
| Terminal-Bench | https://www.tbench.ai/ | 在真实 CLI 环境评测 agent 能否完成命令行任务，偏"操作性任务" |
| agent-eval-harness（opendatahub） | https://github.com/opendatahub-io/agent-eval-harness | "tool once with your pass/fail judgment and a thorough rationale" —— 用 LLM 作为 judge 的打分脚本结构 |
| LLM-as-judge / G-Eval | （学术方法） | 用 rubric + 评分标准让大模型对输出打主观分；可做"测试覆盖不到"的质量维度 |

> 设计原则：**能跑测试就用确定性测试（SWE-bench 式），测不到的再用 LLM-judge 补分（rubric）**，两条腿并行。

## 3. 候选技术栈（待 grill 确认）

- **语言**：Python 或 TypeScript/Node。两者都能做到。倾向：Python 上手快、agent/评测生态最成熟；TypeScript 则与目标产品（Claude Code/OpenCode）同构、终端渲染更顺手。
- **模型接入**：OpenAI 兼容网关（`openai` 库或原生 api + `base_url`），统一覆盖 OpenAI/DeepSeek/Claude/本地模型；**只依赖原生 tool calling 接口**，不引入 agent 框架。
- **运行形态**：CLI 为主；会话可交互（用户确认权限/输入任务），也能一次性非交互跑。

## 4. 开发阶段（分步功能路线图）

### Phase 0 — 脚手架 & 配置（半天）
- 仓库初始化、git、README 骨架。
- 配置层：`.env`/环境变量读 API key、model、base_url、允许工作的目录（`workdir`）。
- 模型客户端封装：单次补全 + 原生 tool calling 调用，统一抽象（不同厂商/网关）。

### Phase 1 — 最小闭环 MVP（1-2 天）
- Agent loop 骨架：`system prompt + history → LLM → 解析 tool call → 本地执行 → 结果回填 → 判断终止 → 循环`。
- 首批 2 个工具：`read_file`、`bash`（shell 执行）。
- 输入解析：优先走模型原生 structured tool calling；预留"文本解析"兜底。

### Phase 2 — 工具集扩展（1-2 天）
- `write_file`、`edit_file`（含精确替换/上下文）、`list_dir`、`grep`、`glob`、`append_file`。
- 工具 schema 设计：参数校验、错误返回、超时（shell 命令）。

### Phase 3 — 上下文管理 + 循环终止 + 错误处理（1-2 天）
- 上下文管理：Token 计数、历史裁剪/摘要、把大输出（长文件、长命令输出）做截断与"已省略"标记。
- 循环终止：最大步数、最大工具调用数、无实质进展、显式"完成"信号、工具连续失败/错误率阈值。
- 错误处理：工具异常、模型输出畸形、超时、重试与降级（结构化失败→文本解析兜底）。

### Phase 4 — 安全 / 权限 / 沙箱（1-2 天，可后续增强）
- 权限模型（候选）：全局允许 vs 逐命令确认 vs 目录白名单；危险命令黑名单。
- 沙箱（可选增强）：docker 容器内执行命令，防止 agent 破坏宿主/泄漏 key。
- 这部分是面试加分/自辩亮点，但优先度排在闭环之后。

### Phase 5 — 自动评测系统（SWE-bench 式）（2-3 天，核心）
- **任务集**：为 agent 准备若干"真实/可复现"的编程任务（生成一个小 repo，带一个待修的 bug 或待补的功能 + 一组隐藏测试）。
- **Harness 流程**：给定任务 → 初始化干净 git 仓库/环境 → 跑 agent → 收集 agent 产生的 diff（或直接看改动后的工作区）→ 应用 patch → 在隔离环境跑测试 → PASS/FAIL。
- **轨迹记录**：完整记录 agent 每一步（对话、工具调用、命令、结果、耗时、token 数），为复盘和面试演示准备。
- **判分**：测试全过为 PASS；否则 FAIL。可再叠加"LLM-judge"对非测试维度（代码质量、是否贴题、风格）打 rubric 分。

### Phase 6 — LLM 裁判（rubric 评分）（1 天）
- 对"无标准测试"或需主观判定的任务，用 LLM-as-judge + 明确评分标准打分（0-5 每维度）。
- judge 提示词：把任务、agent 轨迹、最终改动给 judge，输出各维度得分 + 一句话理由。

### Phase 7 — 演示 & 文档收尾（1-2 天）
- 打磨 CLI 交互与输出可读性。
- README.txt（≤1000 汉字）：仓库地址、如何运行、特色功能、技术选型说明。
- 录 2 分钟视频：让 agent 完成一个真实小任务，讲解闭环/工具/上下文/评测。
- 自辩材料：为什么这样设计（对应面试提问）。

## 5. AI 可驱动的自动评测系统（详细规划）

**目标**：客观、可复现地证明"这个 agent 做的编程任务到底成不成"，并给面试提供数据支撑。

### 5.1 组成
1. **任务定义层**：一个任务 = `{ 仓库快照/种子代码, 任务描述, 隐藏测试/验收标准, 基线 }`。可手工编写，也可自动生成（如基于已有 repo 的某个 commit 回退出一个 bug）。
2. **运行层（harness）**：每个任务一个隔离执行环境（可用临时目录 + 可选 docker）。注入 agent → 让它在这个工作区完成任务 → 记录完整轨迹。
3. **评估层**：确定性评估（跑测试 PASS/FAIL）+ 主观评估（LLM-judge rubric）。
4. **报告层**：聚合结果（通过率、平均耗时、token 数、各维度分数），生成可读报告供复盘与演示。

### 5.2 AI 可驱动的体现
- **AI 生成任务**：用大模型把一段需求/一个 bug 提示词转成"带隐藏测试的任务集"，扩大评测规模。
- **AI 作为 judge**：对测不出的质量维度打分。
- **AI 进行评测编排/倾向分析**：对失败案例做归因，指出 agent 卡在哪类工具/哪步决策上。

### 5.3 判分口径（两套并行）
- **机械判定**：`tests pass → PASS`，否则 FAIL。（SWE-bench 式，最客观）
- **judge 判定**：`rubric 多维度评分`（正确性、完整性、代码质量、是否最小改动、是否符合约定）。（主观，做补充）

## 6. 风险与待确认（grill-me 议题）
1. 技术栈：Python 还是 TypeScript？交互形态？（见 B.1）
2. 模型：日常开发用哪个？agent 运行时用哪个？是否走统一网关？（见 B.2）
3. 评测目标：任务集要先固定下来，避免做完 agent 却不知"用什么任务来证明"。（见 B.3）
4. 安全模型：是否需要沙箱（docker）？权限放开多少？权衡复杂度 vs 演示效果。（见 B.4）
5. 范围裁剪：deadline 前做到哪一档（MVP / 完整 / 带评测精品）。（见 B.5 / B.7）
6. 演示任务：选一个能在 2 分钟内讲清楚的真实小任务。（见 B.6）
